# Phase 2: Canonical Case Assembly
**Status**: VERIFIED & LOCKED
**Date**: August 2026

## Executive Summary
Phase 2 implements the core **Canonical Case Assembly** engine. It establishes a deterministic, rigorous data access layer that reconstructs a fully unified `CanonicalCase` given a single `dispute_id`.

No AI, LLMs, or intelligence modules were introduced in this phase. The focus remained entirely on retrieving and enforcing strict structural topologies based exactly on the Phase 1 Database.

---

## 1. Core Architecture & Schemas

The application backend exposes the Phase 2 logic through FastAPI.

- **Pydantic Schemas (`app/schemas/canonical_case.py`)**: 
  We define strict Pydantic models for the canonical case and every sub-entity (`DisputeSchema`, `TransactionSchema`, `OrderSchema`, `CustomerSchema`, `MerchantSchema`, `DeliverySchema`).
  
- **Strict Typing Constraints**:
  - `Customer` objects are strictly REQUIRED within the `CanonicalCase`. 
  - `Merchant` objects are OPTIONAL because the authoritative source dataset legitimately contains 775 NULL `merchant_id` values.
  - If `order.merchant_id` is NULL, `CanonicalCase.merchant` = None. This is a valid source-data condition.
  - If `order.merchant_id` is NOT NULL, the merchant MUST resolve successfully. Otherwise, it raises a `CaseAssemblyError`.
  
## 2. The Data Access Layer (Repositories)

We built repository abstractions in `backend/app/data_access/repositories/` over the existing Phase 1 SQLAlchemy models.

- **BaseRepository**: Provides standard async `get_by_id`.
- **Entity Repositories**: 
  - `DisputeRepository`
  - `TransactionRepository`
  - `OrderRepository`
  - `CustomerRepository`
  - `MerchantRepository`
  - `DeliveryRepository` (supports custom `get_by_order_id`)

All database interactions happen via SQLAlchemy's `AsyncSession`, ensuring fully non-blocking I/O operations for high throughput.

---

## 3. The CaseService (Assembly Engine)

The `CaseService` (`app/services/case_service.py`) acts as the central orchestrator that performs the deterministic retrieval of all components connected to a dispute.

### Assembly Logic & Relationship Integrity:
The exact path of retrieval is:
1. `dispute_id` -> `Dispute`
2. `Dispute.transaction_id` -> `Transaction`
3. `Dispute.canonical_order_id` -> `Order`
4. `Order.order_id` -> `Delivery` (Optional)
5. `Order.customer_id` -> `Customer`
6. `Order.merchant_id` -> `Merchant`

### Invariants and Error Handling:
If any node in the graph is missing (e.g. the transaction does not exist for the dispute, or the customer doesn't exist for the order), the service explicitly throws a `CaseAssemblyError`.

> [!NOTE]
> During Checkpoint 2.0, we performed an exhaustive audit on the rebuilt Phase 1 PostgreSQL database and verified that **All required relational paths contain zero orphaned foreign-key references**. The source dataset contains 775 legitimate NULL merchant_id values; these are valid source-data conditions rather than orphaned references.

## 4. Deadline Resolver

A centralized utility (`app/services/deadline_resolver.py`) implements the dispute response window calculation.
- **Rule**: `dispute_opened_at + 30 days`.
- **Constraint**: This logic is strictly treated as an application-level configurable benchmark. It does not alter or pollute the underlying database records.

---

## 5. API Endpoint

- **Route**: `GET /api/v1/disputes/{dispute_id}`
- **Operation**: Given a valid ID, it calls the `CaseService`, builds the `CanonicalCase`, and returns a highly structured, fully hydrated JSON root.
- **Error Codes**:
  - `404 Not Found`: Dispute ID does not exist.
  - `500 Internal Server Error`: Thrown when a `CaseAssemblyError` occurs due to structurally missing data (e.g. missing merchant).

## 7. Instructions for Future Phases (Phase 3)
Future agents working on Phase 3 (Intelligence & LLM Integration) should note the following:

1. **Information Root**: Your input will always be the `CanonicalCase` model generated by `CaseService.get_case()`. Do not re-query the database to gather dispute context; trust the `CanonicalCase`.
2. **Context Independence**: The case data you receive is rigorously verified. If `merchant` is null, it means the dataset authentically has no merchant.
3. **No Database Modification**: Do not write intelligence data back into the `disputes` table or raw dataset. 
4. **Tool Access**: Phase 3 will involve LangGraph, embeddings lookup (via the vector DB established in Phase 1), and Groq for LLM execution.
